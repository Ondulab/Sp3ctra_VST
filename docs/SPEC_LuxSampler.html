LuxSampler & FrameSequencer

Enregistrement, stockage et relecture du flux d'images Sp3ctra — avec séquenceur à pas synchronisé DAW.

ComposantsLuxSampler + FrameSequencer
ProjetSp3ctra_VST
Date10 Avril 2026
StatutImplémenté v0.4
Commits05083b0 → f2acf11
Format fichier.fsmp (binaire propriétaire)

§1 Vue d'ensemble

Le sous-système comprend deux composants couplés :

  • LuxSampler — enregistre le flux d'images CIS en provenance de l'UDP, stocke jusqu'à 12 séquences (« banks ») en mémoire, et les rejoue à la demande. Contrôle via MIDI ou via les boutons UI de l'éditeur principal.
  • FrameSequencer NEW v0.4 — séquenceur à pas (max 32 steps) qui orchestre automatiquement l'enregistrement et la lecture des banks LuxSampler selon une grille temporelle synchronisée DAW (PPQ) ou un BPM interne.
ℹ️
Ce que LuxSampler N'enregistre PAS : Il capture uniquement le flux de lignes CIS assemblées (paquets UDP IMAGE_DATA). Ni MIDI, ni audio, ni fragments UDP individuels.

Capacité

  • 12 banks (slots) indépendantes, numérotées 0–11.
  • Durée max : 10 secondes par bank (allocation dynamique à la demande).
  • Canal MIDI configurable (1–16) pour les commandes REC/PLAY.
  • Séquenceur : jusqu'à 32 steps, chaque step assignable à une bank ou laissé vide (passthrough).

§4 Machine d'états par bank

Chaque bank possède sa propre machine d'états. Les transitions sont pilotées par :

  • Les commandes UI (boutons de l'éditeur principal) → Non-RT, via atomiques
  • Le séquenceur FrameSequencer::triggerStep() → RT, via atomiques

Toutes les transitions :
IDLE      → ARMED     : NoteOn REC / UI clic (bank vide)
IDLE      → PLAYING   : NoteOn PLAY (contenu présent) / UI clic / Seq trigger
ARMED     → IDLE       : NoteOff REC / UI stop
ARMED     → RECORDING : NoteOn PLAY / Seq trigger sur ce step / UI clic direct
RECORDING → IDLE       : NoteOff REC | NoteOff PLAY | overflow 10 s | Seq avance step suivant | UI stop
PLAYING   → IDLE       : NoteOff PLAY / UI clic / Seq avance step suivant
PLAYING   → PLAYING   : boucle seamless (fin du buffer → repositionné à 0)
PLAYING   → RECORDING : NoteOn REC pendant PLAYING (punch-in — simplifié)
⚠️
Punch-in (simplifié v0.4) : si NoteOn REC est reçu pendant PLAYING sur le même slot, l'enregistrement démarre depuis le début du buffer (pas à la position courante de la tête de lecture). Le punch-in positionnel (FS-107 de la spec v0.3) est différé à une version future.

§5 Moteur d'enregistrement

5.1 Point de capture — hook C dans udpThread

L'interception se fait dans multithreading.c via un hook C-linkage, appelé après que les 12 fragments UDP d'une ligne ont été réassemblés : 

// lux_sampler_hooks.h – hook appelé par udpThread() dans multithreading.c
extern "C" void lux_sampler_on_frame_assembled(
    const uint8_t* R, const uint8_t* G, const uint8_t* B,
    uint16_t pixel_count, uint32_t line_id);

// Implémenté dans LuxSampler.cpp — dispatche vers LuxSampler::s_instance
// Aucun FrameRecorderThread séparé — capture inline dans le thread UDP
ℹ️
Pas de FrameRecorderThread : contrairement à la spec v0.3, il n'y a pas de thread d'enregistrement séparé. onFrameAssembled() tourne directement dans le thread UDP (Non-RT) et écrit dans le buffer du slot. La latence d'écriture est négligeable.

5.2 Logique de onFrameAssembled()

bool LuxSampler::onFrameAssembled(const uint8_t* R, ...)
{
    // 1. Traiter les commandes startRecCmd / stopRecCmd postées par le RT
    for (int i = 0; i < NUM_SLOTS; ++i) {
        if (startRecCmd[i].exchange(false)) { allocate_if_needed(); activeRecSlot = i; }
        if (stopRecCmd[i].exchange(false))  { finalise_slot(i);    activeRecSlot = -1; }
    }

    // 2. Vérifier qu'un enregistrement est actif
    const int recSlot = activeRecSlot.load();
    if (recSlot < 0) return false;

    // 3. Gate séquenceur — ne capturer que si le seq pointe sur cette bank
    const int gate = seqGateSlot.load();
    if (gate >= 0 && gate != recSlot) return false; // gated out

    // 4. Vérifier overflow (durée / capacité)
    // 5. Écrire la frame dans slots[recSlot].frames[frame_count++]
}

§6 Moteur de lecture — FramePlayerThread

6.1 Architecture

FramePlayerThread est un thread Non-RT dédié (juce::Thread). Il dort 1 ms dans une boucle externe, guette startPlayCmd, puis entre dans une boucle interne qui injecte les frames en respectant leurs horodatages. 

// Boucle externe (idle)
const int slot = startPlayCmd.exchange(-1);
if (slot < 0) { Thread::sleep(1); continue; }

// Boucle interne (lecture active)
while (!threadShouldExit()) {
    if (stopPlayCmd.exchange(false)) break;          // commande stop
    if (slotState[slot] != PLAYING)    break;          // état changé
    if (play_head >= frame_count)  { reset_loop(); continue; } // boucle seamless
    if (elapsed < frame.timestamp_us) { sleep_yield(); continue; } // attendre
    inject_frame_to_audio_buffers(frame);
    update_preprocessed_data(frame);  // via doubleBuffer mutex
    ++play_head;
}
ℹ️
Injection double : pendant PLAYING, FramePlayerThread écrit dans deux endroits :
  1. AudioImageBuffers (via audio_image_buffers_start_write) — remplace le flux UDP live pour la visualisation.
  2. doubleBuffer->preprocessed_data (via image_preprocess_frame + mutex) — ce que synth_AudioProcess lit réellement pour la synthèse.

6.2 Vitesse de lecture

Lecture 1:1, horodatages timestamp_us respectés à la microseconde.

6.3 Boucle seamless

Quand la tête de lecture dépasse frame_count, elle est repositionnée à 0 et l'horloge de boucle est réinitialisée. Le thread ne sort pas de la boucle interne.

Au cycle suivant, FramePlayerThread le consommait immédiatement en entrant dans la boucle interne → silence. §8 Règles de priorité et concurrence

  • Un seul slot peut être en PLAYING à la fois. La note PLAY la plus haute a la priorité.
  • Un seul slot peut être en RECORDING à la fois (activeRecSlot est un unique atomic).
  • Plusieurs slots peuvent être en ARMED simultanément — l'enregistrement effectif ne démarre que sur déclenchement (note PLAY, séquenceur, ou UI).
  • Quand le séquenceur est actif, seqGateSlot bloque la capture sur toutes les banks sauf celle pointée par le step courant.

§10 FrameSequencer — Vue d'ensemble NEW v0.4

Le FrameSequencer est un séquenceur à pas (max 32 steps) qui pilote automatiquement les banks LuxSampler. Chaque step peut être assigné à une bank (0–11) ou laissé vide (passthrough). Le séquenceur avance d'un step à chaque période définie, et déclenche l'action appropriée sur la bank ciblée.

10.1 Actions déclenchées par step

État de la bank cibléeAction déclenchée
ARMED→ RECORDING (post startRecCmd) — début de capture, passthrough maintenu
RECORDING→ reset/restart enregistrement (post startRecCmd)
IDLE (contenu présent)→ PLAYING (post startPlayCmd) — lecture, passthrough coupé
IDLE (vide)→ PLAYING tenté — FramePlayerThread revient à IDLE si pas de contenu (silencieux)
Step vide (bankIdx = −1)→ Passthrough restauré ; stopPlayCmd envoyé si quelque chose jouait

10.2 Arrêt de la bank précédente

triggerStep() maintient rtPrevActiveBank (RT-only, non partagé) pour stopper proprement la bank précédente avant d'activer la suivante :

  • Si la bank précédente était en RECORDING → stopRecCmd posté → onFrameAssembled() finalise le slot (has_content = true)
  • Si la bank précédente était en PLAYING → slotState = IDLE

§11 FrameSequencer — Modes de timing

11.1 Mode DAW sync (par défaut)

Le séquenceur lit AudioPlayHead::getPosition() à chaque processBlock(). Si le transport DAW est en cours (getIsPlaying() == true), la position PPQ détermine le step courant : 

const int absoluteStep = (int)(ppq / beatsPerStep);
const int stepInSeq    = absoluteStep % nSteps;
if (stepInSeq != rtLastTriggeredStep) { triggerStep(stepInSeq); }

Si le transport est stoppé, le séquenceur est en pause (pas arrêté). Il reprend exactement là où la DAW reprend.

11.2 Mode BPM interne

Un accumulateur de phase avance de (bpm / 60 / sampleRate) * numSamples / beatsPerStep beats par bloc audio. Quand la phase dépasse 1.0, le step suivant est déclenché. Le transport DAW n'est pas consulté.

§12 FrameSequencer — Logique complète de triggerStep()

void FrameSequencer::triggerStep(int stepIdx) noexcept
{
    const int bankIdx = steps[stepIdx].load();

    // §1 — Finalise la bank précédente (PLAYING ou RECORDING)
    if (rtPrevActiveBank >= 0 && rtPrevActiveBank != bankIdx) {
        if (prevSt == RECORDING) { stopRecCmd[prev] = true; slotState[prev] = IDLE; }
        if (prevSt == PLAYING)   { slotState[prev] = IDLE; }
    }
    // Safety net : stoppe aussi activePlaySlot si différent
    if (curPlay >= 0 && curPlay != bankIdx) slotState[curPlay] = IDLE;

    // §2 — Step vide (bankIdx = -1)
    if (bankIdx < 0) {
        if (activePlaySlot >= 0) stopPlayCmd = true; // seulement si quelque chose jouait
        activePlaySlot = -1; passthroughEnabled = true;
        rtPrevActiveBank = -1; return;
    }

    // §3 — Bank armée ou en cours d'enregistrement
    if (curSt == ARMED || curSt == RECORDING) {
        slotState[bankIdx] = RECORDING;
        startRecCmd[bankIdx] = true; // passthrough reste ON pendant rec
    }
    // §4 — Bank IDLE (avec ou sans contenu) → lecture
    else {
        stopPlayCmd = false; // annule tout stopPlayCmd obsolète
        slotState[bankIdx] = PLAYING;
        activePlaySlot = bankIdx; startPlayCmd = bankIdx;
        passthroughEnabled = false;
    }
    rtPrevActiveBank = bankIdx;
}
✅
Fix stale stopPlayCmd (commit f2acf11) : avant de poster startPlayCmd, stopPlayCmd est effacé via store(false). Sans cela, un flag obsolète (posté par un step vide précédent) forçait FramePlayerThread à sortir de sa boucle interne immédiatement → silence sur tous les cycles suivants.

Le flux complet d'un enregistrement piloté par séquenceur, bank N sur step 0, séquence de 4 steps :

§15 Interface atomique RT ↔ Non-RT

struct LuxSamplerAtomicState {
    // État par slot
    std::atomic<int>  slotState[NUM_SLOTS];      // IDLE=0, ARMED=1, RECORDING=2, PLAYING=3
    std::atomic<int>  activePlaySlot { -1 };    // -1 si aucun PLAY actif
    std::atomic<bool> passthroughEnabled { true };

    // Commandes pulse (un-shot : RT écrit, Non-RT consomme via exchange)
    std::atomic<bool> startRecCmd[NUM_SLOTS];  // → onFrameAssembled : allocate + start
    std::atomic<bool> stopRecCmd[NUM_SLOTS];   // → onFrameAssembled : finalise slot
    std::atomic<int>  startPlayCmd { -1 };    // → FramePlayerThread : démarre lecture
    std::atomic<bool> stopPlayCmd  { false }; // → FramePlayerThread : stoppe lecture
};

// Dans LuxSampler — gate séquenceur (écrit RT, lu Non-RT)
std::atomic<int> seqGateSlot { -1 }; // -1=pas de gate, 0-11=bank active
🚫
Règle absolue (chemin RT) : processMidi() et triggerStep() n'utilisent que des atomiques. Aucune allocation, aucun mutex, aucun I/O, aucune exception.

§20 Tableau des exigences

MUST — LuxSampler

  • FS-001Les notes C0–B0 (MIDI 12–23) arment l'enregistrement des slots 0–11 sur le canal MIDI configuré. ✓ impl
  • FS-002Les notes C1–B1 (MIDI 24–35) déclenchent la lecture des slots 0–11. ✓ impl
  • FS-003NoteOn PLAY sur un slot ARMED → RECORDING (capture démarre). ✓ impl
  • FS-004L'enregistrement s'arrête sur NoteOff REC / NoteOff PLAY / overflow 10 s / avance séquenceur. ✓ impl
  • FS-005La lecture coupe le passthrough UDP (doubleBuffer) pendant PLAYING. ✓ impl
  • FS-006La lecture boucle seamlessly tant que le slot est PLAYING. ✓ impl
  • FS-007Un seul slot PLAYING à la fois ; note PLAY la plus haute prioritaire. ✓ impl
  • FS-00812 banks indépendantes. ✓ impl
  • FS-009Durée max 10 s par bank. ✓ impl
  • FS-010Un seul canal MIDI actif. ✓ impl
  • FS-011Aucune allocation sur le chemin RT processBlock. ✓ impl
  • FS-012Allocation lazy du buffer au premier enregistrement. ✓ impl
  • FS-013Sauvegarde et chargement .fsmp. ✓ impl
  • FS-014Lecture vitesse 1:1 avec horodatages µs. ✓ impl
  • FS-015Capture du flux IMAGE_DATA UDP (pas MIDI, pas audio). ✓ impl

MUST — FrameSequencer

  • SEQ-00132 steps max assignables à des banks 0–11 ou laissés vides (passthrough). ✓ impl
  • SEQ-002Mode DAW sync : avance sur PPQ AudioPlayHead, pause si transport stoppé. ✓ impl
  • SEQ-003Mode BPM interne : accumulateur de phase indépendant du transport DAW. ✓ impl
  • SEQ-004triggerStep() : bank ARMED/RECORDING → déclenche capture (pas playback). ✓ impl
  • SEQ-005triggerStep() : finalise proprement la bank précédente (RECORDING → stopRecCmd, PLAYING → IDLE). ✓ impl
  • SEQ-006Gate séquenceur (seqGateSlot) : frames capturées seulement quand seq pointe sur la bank armée. ✓ impl
  • SEQ-007stopPlayCmd effacé avant tout startPlayCmd (aucun flag stale). ✓ impl
  • SEQ-008Chemin triggerStep() : atomiques uniquement, RT-safe. ✓ impl

SHOULD

  • FS-101Label par slot (63 chars UTF-8), persisté en .fsmp. ✓ impl
  • FS-102UI : état temps réel des 12 banks (IDLE/ARMED/REC/PLAY) + durée. ✓ impl
  • FS-103Paramètre octaveOffset (−2 à +2). ✓ impl
  • FS-104Vérification CRC32 à l'ouverture des .fsmp. ✓ impl
  • FS-105Slot jamais utilisé = zéro mémoire heap. ✓ impl
  • FS-106Flux UDP live distribué aux autres consommateurs pendant PLAYING. ✓ impl
  • FS-108Fichier .fsmp inclut les 12 blocs même vides. ✓ impl
  • UI-001Clic simple contextuel sur bank (play/rec/stop selon état). ✓ impl
  • UI-002Double-clic (<400 ms) → clear bank. ✓ impl
  • UI-003Grille 32 steps séquenceur dans l'éditeur principal. ✓ impl

MAY — Versions futures

  • FS-107Punch-in positionnel (enregistrement depuis la position courante de la tête de lecture). Différé.
  • FS-201Vitesse de lecture variable (0.5×, 1×, 2×).
  • FS-202Compression zlib optionnelle des payloads .fsmp.
  • SEQ-101Multi-instance LuxSampler (suppression du singleton C).
  • SEQ-102Longueur de step variable par step (polyrhythmie).
